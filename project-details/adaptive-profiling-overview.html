Cloudflare Dynamic Profiling

A serverless, edge-native clone of Imperva's Dynamic Profiling — built entirely on Cloudflare Workers, D1, and KV.

Cloudflare Workers D1 (SQLite) KV Namespaces React + Vite Scheduled Reconciler Anomaly Detection

What is this? Imperva's Dynamic Profiling learns the normal "shape" of every API endpoint — its parameters, field types, lengths, entropy, and behavioural patterns — and flags deviations as anomalies. This project replicates that capability at the Cloudflare edge: a zero-infrastructure, globally distributed system that automatically profiles every HTTP request, builds a trust-weighted statistical model of each endpoint's fields, and surfaces anomalies in a React dashboard — all without any application changes.

The Three Cloudflare Workers

① data-collector

The transparent proxy. Sits in front of the origin. Every request passes through it — zero latency impact because profiling runs in ctx.waitUntil().

  • Normalises paths (UUIDs → :uuid, IDs → :id)
  • Parses JSON / form / multipart bodies
  • Extracts query params, flattened body fields, headers
  • Computes Shannon entropy per field value
  • Writes to D1: endpoints, request_context, request_metrics, parameters, responses
  • Writes per-field rolling buckets to KV (obs:endpoint:{id}:field:{src}:{name})
  • Trust-weights each observation (bot / ASN / TLS signals)

② data-collector-reconciler

A Cron-triggered worker that sweeps KV and promotes observations into D1 field profiles.

  • Iterates all obs:endpoint:* KV keys
  • Computes composite Stability Score (0–4) from field, request, response, & trust signals
  • Promotes field to field_metadata when score ≥ 3
  • Auto-locks field when score = 4 & endpoint hits ≥ 50
  • Detects anomalies on locked fields: out-of-range lengths, entropy spikes, score drops
  • Writes hourly snapshots to field_score_history and field_score_explain
  • Tracks schema changes in field_evolution

③ data-collector-control-plane

A REST API gateway that the React dashboard queries. Enforces API-key auth and CORS.

  • GET /internal-api/endpoints — list all endpoints
  • GET /internal-api/endpoints/:id/parameters
  • GET /internal-api/endpoints/:id/field-metadata
  • GET /internal-api/endpoints/:id/request-context
  • GET /internal-api/endpoints/:id/request-metrics
  • GET /internal-api/endpoints/:id/responses
  • GET /internal-api/endpoints/:id/anomalies
  • GET /internal-api/endpoints/:id/score-history
  • GET /internal-api/endpoints/:id/reconciler-scores
  • POST /internal-api/categories/add — custom file categorisation

④ React Dashboard (CFFrontEnd)

A React + Vite SPA that queries the control-plane and visualises the collected profile data.

  • EndpointProfiler — top-level layout: sidebar + detail panel
  • EndpointBrowser — searchable/filterable list of all discovered endpoints
  • EndpointDetailsPanel — tabbed view: parameters, field metadata, context, metrics, responses, anomalies
  • ScoreHistoryChart — Recharts line chart of stability score over time
  • FieldPromotionInsights — table: score, reason, trust weight, diagnostics per field
  • ParameterTable — reusable sortable data table

End-to-End Data Flow

1

Request Arrives

Any HTTP request hits the data-collector Worker. Static assets (.js, .css, fonts, images) are forwarded immediately with no profiling.

2

Forward & Profile (async)

Request is forwarded to the origin; the response is returned to the client. All profiling runs in ctx.waitUntil() — no added latency to the user.

3

Endpoint Upsert (D1)

Path is normalised and the endpoint row is upserted into D1 with incrementing hit counts, auth ratio, and error rate — all computed in O(1) with online averaging.

4

Context + Metrics (D1)

IP, geo, user-agent, intent classification, TLS version, cipher, ASN, referrer, protocol, cookie count, body size, burst count, header size are written to request_context and request_metrics.

5

Field Observation → KV

Each query param, header, and body field is bumped into a KV bucket keyed obs:endpoint:{id}:field:{source}:{name}. The bucket accumulates value frequencies, type histogram, min/max/avg length, and online Shannon entropy — trust-weighted by the request's bot / ASN / TLS signals. TTL = 1 hour.

6

Reconciler Sweep (Cron)

The scheduled reconciler pages through all KV keys. For each field it computes a Stability Score (0–4) combining field entropy, request burstiness, response error ratio, and trust modifiers.

7

Promotion to field_metadata

Fields with score ≥ 3 are promoted to D1's field_metadata table with inferred type, example value, length bounds, and entropy. Fields with score = 4 on endpoints with ≥ 50 hits are locked.

8

Anomaly Detection

On locked fields, the reconciler checks for: out_of_range (observed length outside learned bounds), entropy_spike (entropy > 1.6× baseline), score_drop (stability declined). Anomalies are stored in the anomalies table with occurrence counts.

9

Score History + Evolution

Hourly snapshots are written to field_score_history (score + delta), field_score_explain (full diagnostics: entropy, diversity, length variance, trust weight), and field_evolution (value/type count trends).

10

Dashboard Visualisation

The React dashboard polls the control-plane API and renders the full field profile: parameters, field metadata, anomaly badges, score-history line charts, and field promotion diagnostics with colour-coded trust scores.

Stability Score — How It Works

The score (0–4) is the core differentiator. It determines whether a field is trustworthy enough to be locked into the profile. Once locked, any deviation triggers an anomaly.
Component Weight What penalises the score
Field Score 40 % Entropy > 4.0; avg length outside [min, max]; observed values > 50 distinct
Request Score 30 % Burst count > 10 req/10 s; body size > 5 KB; query params > 20 or headers > 50
Response Score 30 % Error ratio > 20 %; response body size variance > 3 KB; avg latency > 1 s
Trust Modifier × 0.5–1.0 Bot UA → ×0.5; known bad ASN → ×0.6; outdated TLS (1.0/1.1) → ×0.7
Lock lifecycle: Score ≥ 3 → promoted to field_metadata. Score = 4 & endpoint hits ≥ 50 → field is locked. Any future deviation on a locked field → anomaly logged.

Database Schema (D1 / SQLite)

endpoints

One row per (scope, path, method). Tracks hit_count, total_hits, auth_required_ratio, error_rate, content_type, first/last seen.

parameters

Aggregated per (endpoint, name, location). Stores type, min/max/avg length, entropy, observed & allowed value lists, anomaly count, lock status.

field_metadata

Promoted field profiles. Adds is_required/is_readonly/format inference, required_ratio, stability_score, is_locked flag, value_count, type_count.

request_context

One row per (endpoint, method, IP). Records geo, user-agent, intent, auth_status, TLS version/cipher, ASN, referrer, accept header.

request_metrics

Per-request: body size, query count, body field count, header count, cookie count/bucket, burst count, header size, query length, request hash (dedup).

responses

Per (endpoint, status_code): avg/last latency, hit count, body size min/max, content-type, error ratio — all updated incrementally.

anomalies

Per (endpoint, field, source, reason). Reasons: out_of_range, entropy_spike, score_drop. Stores observed type/value, score delta, occurrence count.

field_score_history

Hourly time-series of stability_score + score_delta per field. Powers the score trend chart in the dashboard.

field_score_explain

Hourly diagnostic rows: entropy, diversity, length_variance, trust_weight, trust_score_avg, reason text. Feeds the Field Promotion Insights panel.

field_evolution

Hourly: value_count, type_count, entropy_avg per field. Tracks schema drift over time.

logical_context

Maps domain + region + environment (dev/stage/prod/preprod). Enables stricter profiling rules for non-prod scopes.

KV Observation Design

KV acts as a high-throughput write buffer. Every request writes a tiny JSON bucket per field. The reconciler batches these into D1. This avoids D1 write storms while keeping the edge fast.

Key format: obs:endpoint:{endpointId}:field:{source}:{fieldName}

Bucket structure (per field, TTL 1 h):

  • total — weighted observation count (trust-adjusted)
  • types — map of JS type → frequency
  • values — top 8 distinct values by frequency
  • minLen / maxLen / avgLen — rolling length stats (online average)
  • entropyAvg — rolling average Shannon entropy
  • lastObserved — epoch ms timestamp

Key Technical Innovations

  • Zero-overhead profiling: ctx.waitUntil() decouples profiling from the request lifecycle — the origin response is returned immediately.
  • Trust-weighted observations: Every KV bucket write is multiplied by a trust score derived from the request's bot likelihood, ASN reputation, and TLS version. Untrusted traffic contributes less to the learned profile.
  • Incremental statistics: Auth ratio, error rate, and average latency are all computed in O(1) using online averaging formulas — no full-table scans.
  • Two-phase write design: KV absorbs high-frequency writes (burst-friendly, low cost); the scheduled reconciler drains them into D1 in batches — a pattern analogous to a write-ahead log.
  • Auto-locking lifecycle: Fields graduate through observed → promoted → locked automatically, mirroring Imperva's profile maturation without manual configuration.
  • Multi-dimensional anomaly detection: Anomalies are not binary; they include entropy spikes (data randomness), length violations, and stability score regression — each with a cause label and occurrence counter.
  • Scope-aware tenancy: The scope column on endpoints (derived from host parsing: domain + environment) allows different profiling strictness per tenant or deployment environment.
