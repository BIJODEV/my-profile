Maintenance Control Panel

A one-click, self-scheduling, self-expiring, fully audited replacement for hand-editing Cloudflare Snippet Rules to take a storefront offline.

Cloudflare Worker React 18 + Vite D1 + Cron

What this replaces

Putting a site into maintenance mode used to mean logging into the Cloudflare dashboard, hand-editing a Snippet Rule's WAF expression, and hoping someone remembered to flip it back off. This panel turns that into a guided UI action: pick a domain, pick a window, click one toggle — with automatic activation and retraction, and a full audit trail of who did what and when.

Everything — the UI, the API, and the automation — runs on Cloudflare's edge. There is no origin server to patch, scale, or keep online for this to work.

Component breakdown

Cloudflare Worker
src/worker.ts · 693 lines

Triple duty: serves the static React build via the ASSETS binding, exposes the JSON API under /api/*, and runs the scheduled() Cron handler. One artifact, one wrangler deploy.

Snippets + Snippet Rules
Cloudflare Rulesets API

Per domain, deploys a Snippet named maint_<domain> that returns a branded 503. A Snippet Rule routes matching traffic to it — enable/disable is just flipping enabled, content is pre-deployed so activation is instant.

D1 database
schema.sql + migrations/

active_interventions holds current window state with a unique index on rule_id for idempotent upserts. audit_logs is a separate, append-only ledger.

React UI
MaintenancePanel.tsx + components/

Command Center, Fleet, and Calendar tabs plus an Audit Log modal — all reading the same edge + D1 state so every tab and machine stays in sync.

Intervention lifecycle

scheduled

Snippet deployed and ready, but the rule is disabled at the edge. D1 row waits for start_time.

active

Rule enabled — the edge serves the branded 503 with Retry-After, before any request reaches origin.

completed

The Cron sweep disabled the rule automatically once expiration_time passed. No human had to be online.

cancelled

An operator manually cancelled the window, from either scheduled or active, via the UI.

Design decisions worth knowing

Trade-offs made deliberately, not overlooked — the reasoning is what a new maintainer needs, not just the fact of the choice.

Read-modify-write on the full rule list

Snippet Rule updates always fetch the entire rule list and PUT it back, matched by stable snippet_name — so this tool can never clobber another team's rules, even though the Rulesets API only exposes a bulk PUT.

Idempotent upserts via unique rule_id

A unique index on rule_id lets every write use INSERT ... ON CONFLICT, so retries and race conditions never produce duplicate rows.

Access header read, not JWT-verified

Actor attribution trusts Cf-Access-Authenticated-User-Email directly — a deliberate trade-off for an internal tool at this scale, not an oversight.

API token never reaches the browser

It's a Worker secret used only in server-side Cloudflare API calls — nothing sensitive ships to the client.

⚠️ Access-header trust model: only sound if Cloudflare Access is the only way to reach this Worker (no open workers.dev bypass route) and the Access policy is a strict allow-list. If this ever needs to be defensible for compliance, the upgrade path is validating Cf-Access-Jwt-Assertion against Access's JWKS instead of trusting the plaintext header.

Typical workflow

  1. Open the Command Center, pick a preset domain or enter a custom one.
  2. Choose "Enable now" or "Schedule window," set date/time, optionally add a custom outage message and Change Reference.
  3. Preview the exact 503 page customers will see, then confirm.
  4. The Worker pre-deploys the Snippet; the rule flips on immediately, or waits for the Cron sweep at start_time.
  5. Watch live countdowns; extend, reschedule, or cancel instantly if plans change.
  6. The Cron Trigger retracts the rule automatically at expiration_time — no one needs to be online.
  7. Every step lands in audit_logs, reviewable in the Audit Trail modal by domain.
